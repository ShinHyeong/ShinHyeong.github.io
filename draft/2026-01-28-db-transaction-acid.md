# 트랜잭션이 신뢰성을 보장하기 위해 반드시 만족하고 있는 조건 : ACID

ACID는 트랜잭션이 안전하게 수행되기 위해, 트랜잭션이 만족하고 있는 조건입니다. 개발자는 트랜잭션의 ACID가 보장하는 안전함을 믿고 비즈니스 로직에 집중할 수 있습니다. 

## 1) 원자성(Atomicity) : All or Nothing

금전적 손실이나 데이터 오류를 방지하기 위해, 트랜잭션 내 모든 작업은 모두 반영되거나 아니면 전혀 반영되지 않아야 한다는 조건입니다(**부분적 성공 금지**).

### 원자성 메커니즘 : Undo Log (History Buffer)

트랜잭션이 원자성을 지킬 수 있는 원리는 무엇일까요?

DB는 데이터를 변경하기 전, 이전 값(Old Value)를 Undo Log에 먼저 기록합니다.

만약 트랜잭션 중 시스템 오류가 발생하거나 롤백이 호출되면, 시스템은 Undo Log를 참조하여 데이터를 이전 값(Old Value)으로 덮어씌웁니다.

그 결과 DB를 마치 아무일도 없었던 것처럼 원래 상태로 복구할 수 있습니다.

## 2) 일관성(Consistency) : 항상 규칙을 벗어난 데이터는 없다

트랜잭션이 **일어나는 동안** 또는 **커밋**된 후에도 DB는 이미 설정한 **비즈니스 로직 조건을 항상 유지**해야한다는 조건입니다.

ex. 데이터 타입은 이메일 형식을 준수해야한다. 

규칙을 위반하면 즉시 롤백되어 일관된 상태(규칙 지킨 상태)로 되돌아갑니다.

## 3) 격리성(Isolation) : 아직 커밋되지 않으면 다음 트랜잭션 실행하면 안됨

동시에 수많은 트랜잭션들이 실행되더라도, **각 트랜잭션은 서로 중간 상태(아직 커밋되지 않은 데이터)에 영향을 주지 못하게** 해야한다는 조건입니다.

마치 100명이 동시에 DB를 사용해도, 사용자는 혼자 쓰는 것처럼 느껴야 합니다.

Spring의 @Transactional(isolation = …) 속성으로 격리성 정도를 제어할 수 있습니다.

### 만약 격리성이 깨진다면 : Race 컨디션 발생

- t1 : 1000원 입금
- t2 : 500원 출금
- Result should be 1500, but 500?🤔

t1 커밋 완료 → t2 순서대로 이루어져야하는데, t1이 커밋되기도 전에 t2가 실행되었습니다. 트랜잭션들이 동시에 이루어져서 t2가 t1의 작업 결과를 덮어쓰는 사태가 발생했습니다. 

이처럼 격리성이 보장되지 않으면 데이터의 정합성이 붕괴됩니다. 

## 4) 지속성(Durability) : 장애나도 DB는 영구보존

**시스템 장애가 발생**하더라도, **이미 커밋된 트랜잭션**은 **영구적으로 보존**되어야한다는 조건입니다.

### 지속성 매커니즘 : WAL (Write-Ahead Logging)

만약 시스템 장애가 발생해서 시스템을 껐다가 다시 키면, DBMS는 미리 작성해두었던 로그(Log)를 분석합니다. 

이렇게 로그만 살아있다면, **커밋은 완료되었으나** 실제 디스크(Data File)에는 아직 **기록되지 않았을 수 있는 데이터**를 로그를 보고 **다시 반영**합니다 (=Redo, 재실행)
