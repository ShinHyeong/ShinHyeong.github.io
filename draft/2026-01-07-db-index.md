# 인덱스 (Index)

> SQL에서 데이터를 더 빠르게 찾기 위해 사용하는 목차 같은 구조
> 
- 조회는 빨라지지만 쓰기 속도와 저장공간에는 비용이 든다.

### 📚 비유로 이해해보자

> 책 전체를 다 읽으며 원하는 내용을 찾는 건 느리지만,
> 
> 
> 목차(index)를 보고 바로 필요한 페이지를 찾는 건 훨씬 빠르다
> 

SQL에서도 마찬가지:

- 인덱스 없으면: 테이블 전체를 다 뒤짐 (**Full Table Scan**)
- 인덱스 있으면: 정리된 "주소 목록" 보고 바로 접근 (**Index Scan**)

## ✅ 1) 인덱스를 왜 쓰는 이유 (목적)

- 📈 **조회 성능 향상**
    
    → `WHERE`, `ORDER BY`, `JOIN`, `GROUP BY`에 자주 쓰이는 컬럼에 유리
    
- 📉 **전체 테이블 스캔(FULL SCAN)을 피할 수 있음**
- 📦 **중복 방지(UNIQUE INDEX)** 가능

---

## 🔍 2) 어떤 상황에서 인덱스를 쓸까?

- `WHERE 조건` 자주 사용하는 컬럼
- `JOIN`에 사용되는 키
- `ORDER BY`, `GROUP BY` 대상
- 자주 검색되는 외래키, 로그인 컬럼 등

```sql
-- 기본 인덱스 생성
CREATE INDEX idx_email ON users(email);

-- 유니크 인덱스
CREATE UNIQUE INDEX idx_username ON users(username);
```

---

## 🚨 3) 인덱스의 단점

| 단점 | 설명 |
| --- | --- |
| 🐢 **쓰기 성능 저하** | `INSERT`, `UPDATE`, `DELETE` 시 인덱스도 함께 수정됨 |
| 💾 **저장 공간 사용** | 인덱스는 별도로 저장 공간을 차지 |
| ⚠️ **과도한 인덱스는 역효과** | 인덱스가 너무 많으면 오히려 느려지고 관리 어려움 |

---

## 📊 4) 인덱스 종류

| 인덱스 종류 | 설명 |
| --- | --- |
| **기본 인덱스 (**B+ Tree 인덱스**)** | 일반 검색용 인덱스 |
| **유니크 인덱스** | 중복값 허용 안 함 |
| **복합 인덱스** | 여러 컬럼을 묶어서 인덱싱 |
| **클러스터형 인덱스** | 테이블 자체가 인덱스로 정렬됨 (MySQL InnoDB 등) |
| **비클러스터형 인덱스** | 인덱스와 데이터 따로 저장됨 |

---

### 📘 B-Tree 인덱스

- 대부분의 DBMS 기본 인덱스
- 균형 트리 구조
- 값 탐색, 정렬, 범위 검색에 강함

### 📘 B+ Tree 인덱스

- B-Tree 개선형
- **리프 노드에만 데이터 저장**
- **순차 탐색, 범위 조회에 더 효율적**

### 📘 복합 인덱스 (Composite Index)

- 여러 컬럼으로 구성된 인덱스
- **선두 컬럼부터 순서 중요**
    - `(col1, col2)` 인덱스는 `col1` 단독/`col1 + col2` 검색엔 유리, `col2` 단독은 비효율

## 🌳 1. B-Tree (Balanced Tree)

> 균형 잡힌 다진 트리 자료구조로,
> 
> 
> 모든 노드가 정렬된 키(key)를 가지고 있고,
> 
> **루트에서 리프까지 깊이가 같다.**
> 

→ 디스크 I/O 최소화를 위해 설계됨 → **데이터베이스 인덱스에 적합**

- 노드 하나에 여러 키와 자식 노드를 가짐 (이진트리보다 효율적)
- **내부 노드와 리프 노드에 모두 데이터 저장**
- **데이터가 많아져도 트리 높이가 작음** → 탐색 성능 유지

---

## 🌳🌿 2. B+ Tree (B-Plus Tree)

> B-Tree에서 발전된 구조로, 대부분의 DBMS에서 실제 사용하는 인덱스 구조
> 

---

### ✅ 주요 차이점

| 항목 | B-Tree | B+Tree |
| --- | --- | --- |
| 📄 데이터 저장 위치 | 내부 노드 + 리프 노드 | ✅ 리프 노드에만 저장 |
| 🧭 범위 탐색 | 비효율적 (순차 탐색 어려움) | ✅ 효율적 (리프 노드 연결되어 있음) |
| 🔗 리프 노드 연결 | ❌ 없음 | ✅ 있음 (Linked List 구조) |
| ⬇️ 트리 깊이 | 더 작을 수 있음 | 약간 깊어질 수 있음 |

---

### 📌 B+Tree는 이렇게 생김

```
        [20|40]
        /   |   \
     [5|10] [25|30] [45|50|60]
        ↘    ↘      ↘
        데이터 저장은 리프 노드에만!

```

→ 리프 노드들이 **연결 리스트처럼 순차 연결**되어 있어서

범위 검색에 아주 유리! (예: WHERE age BETWEEN 20 AND 30)

---

## ✅ 왜 DBMS는 B+Tree를 쓸까?

- 모든 데이터를 리프 노드에만 저장하므로 **트리 구조가 더 일관됨**
- **범위 검색, 정렬 처리에 유리**
- 인덱스 스캔 시 **디스크 I/O를 최소화**할 수 있음
- MySQL(InnoDB), Oracle, PostgreSQL 모두 B+Tree 기반 인덱스 사용

---

## 💡 정리: B-Tree vs B+Tree 요약

| 구분 | B-Tree | B+Tree |
| --- | --- | --- |
| 데이터 저장 | 모든 노드 | 리프 노드에만 저장 |
| 검색 속도 | 빠름 | ✅ 빠르고 일정함 |
| 범위 검색 | 느릴 수 있음 | ✅ 매우 빠름 (리프 연결 구조 덕분) |
| 실사용 | 일부 오래된 시스템에서 사용 | ✅ 거의 모든 DBMS에서 사용됨 |

---

## ✅ 한 줄 요약

> B+Tree는 B-Tree의 개선형으로,
리프 노드에만 데이터를 저장하고 순차 연결해서,
범위 검색과 빠른 탐색에 최적화된 인덱스 구조.
